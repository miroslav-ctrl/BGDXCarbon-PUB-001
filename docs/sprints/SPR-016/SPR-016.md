Status: proposed plan only, 2026-10-19. No implementation or acceptance complete.

## Current state and proposed next step

publishing/docx.py provides frozen DocxRequest, DocxRenderer.render -> bytes and
DocxPublishingService.publish -> PublishResult. cli/publish.py resolves the legacy
DOCX service; HTML already has typed job orchestration. Runtime registers the
legacy DOCX service. Existing tests/publishing/test_docx.py verify content,
metadata, editable structure, link/image safety, overwrite, aliases and errors.

Add a separate docx_pipeline service with validate/read/render/write stages,
immutable envelopes, structured errors and safe logs. Register it alongside the
legacy service and provide an installed-wheel Python API example.
This is the API foundation step, analogous to SPR-012. CLI migration is explicitly
deferred to a separately approved sprint to preserve publish-docx behavior now.

## Scope and compatibility

Reuse existing DocxRequest, DocxRenderer, atomic byte writer, job/orchestration
services and engine-owned contexts. Preserve existing CLI signature, arguments,
routing, stdout/stderr, exits and lifecycle behavior. Preserve direct
DocxPublishingService API, PublishResult and PublishingError/cause behavior.
Do not redirect the legacy service through the new pipeline.

No new dependency, engine rewrite, renderer redesign, new CLI option, HTML/PDF/
batch migration, DOCX batch, queue/storage, retry, parallelism, cancellation,
rollback, version bump or release. main is outside scope.
